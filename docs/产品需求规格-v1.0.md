## 1. 文档目的

本文档是 fz-workSpace 当前开发、验收和后续变更的需求基线，包含 v1.0 初始需求以及截至 2026-08-11 已确认并实现的增量变更。

后续任何变更必须：

1. 先记录变更原因和影响范围。
2. 标明影响的需求编号与验收项。
3. 更新文档版本后再修改代码。
4. 不得借局部需求顺带重构或改动无关页面。

## 2. 需求来源与优先级

当不同资料出现冲突时，按以下顺序处理：

1. 本文档中已确认的功能行为与验收标准。
2. v1.0 视觉基线设计图中的布局、层级和视觉方向。
3. 用户后续已记录并确认的变更单。
4. 实现层面的默认选择。

视觉图负责定义初始视觉方向，本文档负责定义当前行为。视觉图中没有表达的加载、空状态、错误处理和安全边界，以本文档为准。原设计图中的右侧详情面板已改为居中的实色弹窗；背景使用半透明遮罩，不再使用灰色毛玻璃或整体模糊。

## 3. 产品定义

fz-workSpace 是一款面向开发者的 macOS 个人工作台，将以下重复流程整合为一个可视、可审查、可恢复的工作流：

1. 从公司知识库同步分配给当前用户的 Bug、需求、支持及其他工单。
2. 使用独立设计的卡片界面浏览、筛选和查看工单，而不是直接展示知识库网页。
3. 为工单选择对应本地 Git 仓库、分支以及 Codex 或 Cursor。
4. 补充模块、文件或技术约束等辅助信息后，后台启动 AI 修改代码。
5. 查看 AI 的修改报告、代码差异、测试结果和影响分析。
6. 由用户人工确认后执行本地 commit、拉取最新代码和 push。
7. push 成功后，将知识库工单改为“待测试”，并按工单类型决定是否转交及转交对象。

核心原则：AI 可以修改和建议，但 commit、push 和工单流转必须经过用户明确批准。

## 4. 产品目标

- 用独立桌面 UI 替代日常在知识库网页中查找工单的操作。
- 降低从工单信息到 AI 编程提示词的重复整理成本。
- 让 AI 修改过程、结果和风险透明可审查。
- 将 Git 提交和工单流转连接为可靠、可中断、可重试的流程。
- 保证用户现有代码和未提交改动不被意外覆盖。

## 5. 本次范围

### 5.1 包含

- macOS 桌面应用。
- 知识库登录会话、工单同步和页面自动化更新。
- 重新设计的工单卡片、筛选、搜索、项目导航和工单详情弹窗。
- 项目与一个或多个本地 Git 仓库的映射。
- Codex 与 Cursor 两种 AI 工具。
- AI 后台运行、进度日志、取消、结果报告和人工审批。
- Git commit、同步远程最新代码、冲突阻断和 push。
- push 后更新知识库工单状态及负责人。
- 浅色模式、暗黑模式和跟随系统模式。
- 本地配置、执行历史与失败恢复。
- AI 完成、需要确认、发生冲突等 macOS 本地通知。

### 5.2 明确不做

- Windows、Linux、Web、iOS 或 Android 版本。
- 将知识库网页作为应用主界面或简单 WebView 套壳。
- 自动解决 Git 冲突。
- 自动创建合并请求或自动合并代码。
- 未经人工审批自动 commit、push 或更新工单。
- 多用户团队后台、云同步和跨设备同步。
- 完整 IDE 或通用代码编辑器。
- 接入 Codex、Cursor 以外的 AI 编程工具。
- App Store 上架、企业签名、自动更新服务。
- 知识库 API 接入；若未来获得 API 权限，另立变更项。
- 多个 AI 任务同时修改同一个仓库。

## 6. 用户与运行前提

- 首版为单用户工具，用户是开发者本人。
- 本机已安装 Git，并拥有目标远程仓库的拉取和推送权限。
- Codex 和 Cursor 需要已安装并完成各自登录；应用负责检测，不保存其账号密码。
- 知识库当前只能通过已登录网页读取和操作。
- 知识库存在“待测试”状态，且用户有权限修改状态和负责人。
- 首版优先支持 Apple Silicon Mac 和 macOS 13 及以上版本。

## 7. 信息架构与页面

### 7.1 主工作台

与视觉基线一致，主界面使用左侧导航和中央工单区的两段式桌面布局；工单详情通过弹窗呈现：

- 左侧：全局导航和项目列表。
- 中间：顶部搜索筛选区与工单卡片网格，占据剩余空间。
- 居中弹窗：选中工单的详情与“开始解决”配置面板。

弹窗打开后保持当前列表、筛选条件、滚动位置和选中卡片，不跳转到新的页面。

### 7.2 项目与仓库配置

用于维护知识库项目与本地 Git 仓库之间的映射，包括：

- 知识库项目名称与标识。
- 一个或多个本地仓库路径。
- 仓库显示名称。
- 默认仓库。
- 默认基础分支。
- 远程名称，默认 `origin`。
- 默认测试负责人，可选。

### 7.3 设置

包含：

- 知识库列表地址与登录状态。
- 立即同步，以及 1–8 小时可选的自动同步间隔；间隔修改必须点击“保存”后生效，未修改时保存按钮不可用。
- Codex、Cursor 可用性和可执行程序路径。
- 默认 Git 行为。
- 浅色、暗黑、跟随系统主题。
- 本地通知开关。
- 日志与本地数据管理。

### 7.4 AI 报告与审批

AI 完成后进入独立的报告视图或覆盖层，至少包含：

- 解决结论。
- 修改文件列表。
- 每项修改的内容和原因。
- 可展开的代码差异。
- 已执行测试及结果。
- 未执行测试及原因。
- 潜在影响和风险。
- 建议人工检查项。
- “继续修改”“放弃修改”“批准并提交”操作。

### 7.5 执行历史

记录每次工单处理的关键节点：

- 工单编号和标题。
- 项目、仓库、分支、使用的 AI 工具。
- 开始与结束时间。
- 最终状态。
- commit hash 和 push 结果。
- 工单状态更新结果。
- 可重新打开的报告和错误信息。

## 8. 视觉与交互规范

### UI-001 独立桌面界面

- 知识库网页只作为数据源和登录入口。
- 主界面不得展示现有知识库表格或网页内容。
- “在知识库中查看原工单”可以在系统浏览器中打开原始工单页面。

### UI-002 左侧导航

视觉基线中的导航项保持如下结构：

- 全部工单。
- 我的处理中。
- 等待我确认。
- 已完成。
- 项目列表及每个项目的工单数量。
- 项目与仓库配置。
- 设置。

定义：

- “我的处理中”：已经启动 AI 或处于本地处理流程中的工单。
- “等待我确认”：AI 已生成报告，正在等待用户审批的工单。
- “已完成”：代码已 push 且工单状态已成功更新的本地执行记录。

### UI-003 顶部工具栏

- 标题和当前待处理数量。
- 按标题或编号搜索。
- 两行知识库同步状态：第一行显示状态，第二行显示上次同步时间。
- 手动刷新按钮；同步期间刷新图标持续旋转，同步结束后恢复，不显示阻塞全屏弹窗。
- 通知入口；同步发现新工单时显示红点，点击后展示新工单标题、类型和优先级，并清除红点。
- 用户入口。
- 类型、优先级、状态、版本筛选。
- 排序方式，默认按知识库查询顺序或最新更新时间。

### UI-004 工单卡片

每张工单以独立卡片展示，至少包含：

- 工单编号。
- 所属项目。
- 类型：Bug、需求等。
- 优先级。
- 标题。
- 最多三行的描述摘要。
- 当前状态。
- 目标版本。
- 更新时间。
- “去解决”按钮。

交互要求：

- 单击卡片打开工单详情弹窗。
- 选中卡片使用明确的蓝色边框和背景变化。
- “去解决”打开同一张工单的详情弹窗，并自动聚焦解决配置区域。
- “待测试”工单不显示“去解决”，详情中也不显示 AI 配置、报告和交付操作区。
- 更新时间使用工单自身最新更新时间：当天显示“刚刚”或“X 小时前”，非当天显示 `yyyy-MM-dd HH:mm`。
- 不能只通过颜色区分类型、优先级或状态，必须同时显示文字标签。

### UI-005 工单详情弹窗（CR-001、CR-008）

弹窗规则：

- 使用居中弹窗，不再使用固定右侧详情面板或右侧抽屉。
- 弹窗宽度随窗口在约 780–960px 之间调整，高度不超过窗口可视区域并保留外边距。
- 弹窗外只使用半透明深色遮罩，不使用毛玻璃或背景模糊。
- 弹窗主体使用清晰的实色抬升表面、细边框和阴影，避免偏灰和内容对比不足。
- 弹窗打开时，主列表保持可见但降低对比度；不可操作的背景区域不响应点击。
- 支持右上角关闭、按 Esc 关闭和点击遮罩关闭。
- 若已填写辅助信息、任务正在运行或存在未保存选择，关闭前必须提示确认，避免误丢数据。
- 弹窗打开后焦点进入标题或第一个可操作控件，并支持键盘导航。

弹窗内容包含：

- 完整工单标题和描述。
- 项目、类型、优先级、状态、目标版本、当前负责人、创建人和最后更新时间。
- 代码仓库选择。
- 当前分支和切换分支入口。
- Codex/Cursor 切换。
- 最多 500 字的辅助 AI 定位信息；支持选择本地文件夹，按每行一个标准化路径追加到输入内容。
- “开始解决”主按钮。
- “在知识库中查看原工单”次级按钮。
- AI 解决流程说明。

当 AI 已启动时，弹窗切换为任务进度和日志状态；AI 完成后在同一弹窗或报告弹窗中展示结果，不打开新的网页。

### UI-006 响应式桌面布局

- 左侧侧栏固定为 250pt，不随窗口宽度压缩；顶部右侧同步、刷新、通知和用户入口保持固定尺寸，搜索框优先缩窄。
- 中央内容区不为详情面板预留固定宽度，工单卡片宽度随剩余可用空间伸缩。
- 卡片最小参考宽度为 360pt，每行最多四列；窗口缩小时依次降为三列、两列或一列。
- 卡片最小高度为 296pt，内容允许纵向撑开，不得裁切或遮挡底部内容。
- 卡片行列间距固定为 16pt，网格四周留白为 24pt，卡片不得上下重叠。
- 窗口较窄时详情仍使用居中弹窗，弹窗宽度随窗口缩小并保留内边距，不改回右侧抽屉。
- 建议最小窗口尺寸为 1024 × 700；低于最小尺寸时阻止继续缩小。
- 支持 Retina 显示、窗口最大化和外接显示器。

## 9. 暗黑模式

### THEME-001 主题选择

设置中提供：

- 跟随系统，默认值。
- 浅色。
- 暗黑。

系统主题变化时，跟随系统模式应即时更新，无需重启应用。

### THEME-002 覆盖范围

以下内容必须全部适配暗黑模式，不能只替换页面背景：

- 左侧导航、工具栏、卡片和工单详情区域。
- 详情弹窗、半透明遮罩和弹窗内控件。
- 输入框、下拉菜单、筛选器、按钮和弹窗。
- 状态标签、优先级标签和选中态。
- AI 实时日志、代码差异、语法高亮和测试结果。
- 加载骨架、空状态、错误提示和通知。
- 滚动条、分割线、边框、阴影和禁用态。

### THEME-003 推荐语义色

实现时使用语义颜色变量，不在组件中散落硬编码颜色。

| 语义 | 浅色建议 | 暗黑建议 |
|---|---|---|
| 页面背景 | `#F5F7FA` | `#0F1115` |
| 导航背景 | `#F8FAFC` | `#14171D` |
| 主要表面 | `#FFFFFF` | `#1A1E26` |
| 抬升表面 | `#FFFFFF` | `#202530` |
| 主文字 | `#111827` | `#F3F4F6` |
| 次文字 | `#667085` | `#A7AFBF` |
| 边框 | `#E5E7EB` | `#2B3240` |
| 主色 | `#2563EB` | `#4F8CFF` |

- 状态色在两种主题下分别校准，不直接复用同一色值。
- 正文与背景的对比度目标不低于 WCAG AA。
- 焦点状态必须可见，不能只依赖极弱阴影。

## 10. 功能需求

### FR-100 知识库会话与同步

- FR-101：首次使用时在独立登录窗口打开知识库登录页。
- FR-102：复用登录后的 Cookie/会话，不保存明文密码。
- FR-103：应用启动时先读取并展示最近一次成功同步的本地工单缓存，再自动在后台同步指定查询地址中的全部工单。
- FR-104：同步不限制在第一页；应用沿知识库分页顺序读取所有页面，按工单编号去重，并在成功后替换列表与缓存。
- FR-105：用户可手动刷新；刷新在后台执行并保留现有列表，刷新图标在同步期间持续旋转，同时展示同步中、已同步、失败和登录过期状态。
- FR-106：默认每 2 小时自动同步一次；用户可在设置中选择 1–8 小时，只有点击保存后新间隔才生效。
- FR-107：登录失效时保留最近一次成功同步的缓存工单供浏览，同时明确提示重新登录；在恢复会话并同步成功前，不把缓存视为最新远程状态。
- FR-108：页面结构变化或网络失败时显示明确错误，并继续保留上一次成功同步的数据。
- FR-109：同步发现新工单时记录本次新增列表，在通知图标上显示红点；点击通知后展示标题、类型和优先级并清除红点。

### FR-200 工单浏览

- FR-201：按项目导航和显示项目数量。
- FR-202：支持标题和工单编号搜索。
- FR-203：支持类型、优先级、状态和版本筛选。
- FR-204：支持按更新时间等字段排序。
- FR-205：支持分页或继续加载全部查询结果。
- FR-206：选中卡片后显示完整详情，不丢失当前筛选和滚动位置。
- FR-207：无结果时区分“没有工单”和“筛选后无匹配结果”。
- FR-208：详情显示工单创建人；若列表页缺失创建人，应从工单详情页回退读取。
- FR-209：更新时间直接使用每张工单的最新更新时间；当天显示相对小时，非当天显示完整日期时间。
- FR-210：状态为“待测试”的工单不可重新启动 AI 解决流程。

### FR-300 项目与仓库

- FR-301：每个知识库项目可映射一个或多个本地 Git 仓库。
- FR-302：可设置默认仓库，但开始解决前必须确认本次仓库。
- FR-303：验证仓库路径、Git 状态、远程地址和基础分支。
- FR-304：仓库不可用时禁止启动 AI 并指出具体原因。
- FR-305：不得自动覆盖、删除或 stash 用户已有的未提交改动。
- FR-306：默认在隔离工作区或工单独立分支中执行 AI 修改。
- FR-307：分支名称建议包含工单编号，并允许用户调整。

### FR-400 AI 任务

- FR-401：每次任务可选择 Codex 或 Cursor。
- FR-402：启动前组合工单标题、描述、项目、辅助定位和仓库上下文形成任务输入。
- FR-403：辅助信息可为空，最大长度 500 字；支持选择本地文件夹并写入标准化路径。
- FR-404：后台运行 AI，主界面保持可操作。
- FR-405：实时显示准备、分析、修改、测试、生成报告等阶段和日志。
- FR-406：支持安全取消；取消后不执行 commit、push 或工单更新。
- FR-407：AI 工具未安装、未登录、启动失败、超时或异常退出时给出可操作提示。
- FR-408：同一仓库同一时间只允许一个写入型 AI 任务。
- FR-409：AI 完成后生成统一格式的报告，不依赖原始终端输出作为唯一结果。

### FR-500 报告与人工确认

- FR-501：报告包含修改摘要、原因、文件列表、代码差异、测试和影响分析。
- FR-502：用户可以要求 AI 继续修改，并保留上一轮上下文。
- FR-503：用户可以放弃修改，应用不得提交或更新工单。
- FR-504：只有点击“批准并提交”后才能进入 Git 流程。
- FR-505：测试失败时突出警告并要求再次确认，不隐藏失败结果。
- FR-506：审批前允许编辑 commit 信息；仅需要人工指定负责人的工单类型显示负责人输入，需求、Bug 和支持按固定规则展示交付对象。

### FR-600 Git 交付

严格执行以下顺序：

1. 创建本地 commit。
2. 从对应远程拉取最新代码。
3. 无冲突时 push。
4. push 成功后更新知识库工单。

细则：

- FR-601：默认 commit 信息包含工单编号和标题，并允许用户编辑。
- FR-602：commit 失败时停止，不拉取、不 push、不更新工单。
- FR-603：commit 成功后拉取远程最新代码。
- FR-604：发生合并或 rebase 冲突时立即停止，绝不 push。
- FR-605：冲突提示列出冲突文件、仓库、分支和下一步人工处理建议。
- FR-606：应用不得自动选择一方内容或自动解决冲突。
- FR-607：拉取成功且没有冲突时执行 push。
- FR-608：push 被拒绝、网络失败或权限不足时停止，不更新工单。
- FR-609：每一步均展示状态并防止重复点击导致重复执行。

### FR-700 工单流转

- FR-701：只有 push 成功后才能修改工单。
- FR-702：将工单状态改为“待测试”。
- FR-703：需求工单只修改为“待测试”，负责人保持不变。
- FR-704：Bug 和支持工单修改为“待测试”并转交工单创建人；远程工单缺少创建人时禁止批准交付并提示先刷新。
- FR-705：建议、任务等其他类型可使用审批时人工指定的负责人；负责人为空时保持不变。
- FR-706：状态及规则要求的负责人更新成功后，本地任务才标记为“已完成”。
- FR-707：代码已 push 但工单更新失败时标记为“部分完成”。
- FR-708：“部分完成”只允许重试工单更新，不得重复 commit 或 push。
- FR-709：工单在处理期间已被他人修改时，更新前提示最新状态和潜在覆盖内容。

### FR-800 通知与恢复

- FR-801：AI 完成、等待审批、Git 冲突、push 失败和任务完成时可发送本地通知。
- FR-802：应用重启后恢复任务记录和最后已完成步骤。
- FR-803：恢复后不得自动继续具有外部副作用的步骤。
- FR-804：所有重试操作必须明确显示将要重试的单一步骤。
- FR-805：应用重启时恢复最近一次成功同步的工单缓存，并在用户无感知的情况下发起后台更新。

## 11. 任务状态机

主流程状态：

```text
未开始
  → 准备仓库
  → AI 运行中
  → 报告待确认
  → 用户批准
  → 本地提交中
  → 拉取最新代码
  → 推送中
  → 更新工单中
  → 已完成
```

允许的分支：

- AI 运行中 → 已取消 / AI 失败。
- 报告待确认 → 继续修改 / 放弃。
- 拉取最新代码 → 冲突待人工处理，且不可 push。
- 推送中 → 推送失败，可在确认仓库状态后重试。
- 更新工单中 → 部分完成，只重试工单更新。

任何失败状态都必须保留已完成步骤，不能让用户误以为整个流程未执行。

## 12. 加载、空状态与异常

### LOAD-001 加载状态

- 首次进入时优先显示最近一次成功同步的缓存卡片；无缓存且正在首次同步时显示加载状态。
- 刷新时保留现有卡片，使用非阻塞同步提示和旋转的刷新图标，不显示全屏遮罩。
- AI 与 Git 长任务显示当前阶段、持续时间和最新日志。

### EMPTY-001 空状态

- 没有待处理工单：显示正常完成态和刷新入口。
- 筛选无结果：显示清除筛选入口。
- 没有配置仓库：显示前往项目与仓库配置的引导。
- 没有执行历史：说明历史将在首次处理工单后出现。

### ERR-001 异常状态

- 知识库登录过期。
- 网络不可用。
- 页面解析失败。
- 本地仓库不存在或不是 Git 仓库。
- AI 工具不可用或异常退出。
- 用户取消任务。
- 测试失败。
- commit 失败。
- 拉取冲突。
- push 失败。
- 代码 push 成功但工单更新失败。

每个异常必须包含：发生在哪一步、已完成哪些步骤、哪些步骤尚未执行、可执行的下一步。

## 13. 安全与数据边界

- 知识库登录凭据不得以明文保存到配置或日志。
- 敏感 Cookie、Token、环境变量和仓库凭据不得出现在 AI 报告或普通日志中。
- 应用只在用户选择的仓库范围内读写文件。
- 不自动删除用户分支、工作区或未提交代码。
- 执行 Git 和 AI 命令时记录命令类别与结果，但对敏感参数脱敏。
- 所有产生外部副作用的操作都必须可追溯到工单和用户审批记录。

## 14. 验收清单

### AC-01 视觉与主题

- [ ] 主界面与 v1.0 设计图的导航、卡片网格、顶部工具栏和信息层级一致。
- [ ] 点击工单卡片或“去解决”后，详情以居中的实色弹窗出现，而不是右侧页面、固定侧栏或抽屉；背景仅使用半透明遮罩。
- [ ] 主界面不是知识库网页套壳。
- [ ] 工单卡片根据中央剩余宽度自适应，每行最多四列；侧栏和顶部操作按钮不被压缩，卡片间距固定且不重叠。
- [ ] 卡片内容能够纵向撑开，底部更新时间和操作按钮不被遮挡。
- [ ] 支持浅色、暗黑和跟随系统，并覆盖所有主要页面与状态。
- [ ] 暗黑模式下文字、状态、选中态、代码差异和日志均清晰可读。

### AC-02 工单数据

- [ ] 登录后能够同步指定查询中的真实工单。
- [ ] 对用户名下工单查询，能够遍历所有分页并显示全部工单，不因固定 `page=1` 只显示第一页。
- [ ] 重启应用后立即显示上次成功同步的缓存工单，并自动在后台更新。
- [ ] 默认每 2 小时同步，可保存 1–8 小时的自定义间隔；手动刷新期间刷新图标旋转且界面保持可操作。
- [ ] 发现新工单时通知图标显示红点，列表包含标题、类型和优先级，点击后红点消失。
- [ ] 卡片字段与知识库数据一致。
- [ ] 详情展示工单创建人；更新时间当天显示相对小时，非当天显示 `yyyy-MM-dd HH:mm`。
- [ ] 搜索、筛选、排序和项目导航结果正确。
- [ ] 登录失效、空列表与解析失败能够被正确区分；缓存可继续浏览，但界面明确标记需要重新登录或同步失败。
- [ ] 选择卡片后弹出对应工单详情，不丢失列表、筛选和滚动状态。
- [ ] 弹窗支持关闭、Esc 关闭和遮罩关闭；存在未保存输入或运行中任务时会先提示。

### AC-03 仓库与 AI

- [ ] 每个项目可配置多个仓库并在处理前选择。
- [ ] 无效仓库或可能覆盖用户改动时阻止执行。
- [ ] Codex 与 Cursor 均能启动真实任务并返回过程状态。
- [ ] AI 完成后报告包含修改、原因、差异、测试和影响。
- [ ] 继续修改、取消和放弃不会触发 Git 或知识库副作用。

### AC-04 人工审批与 Git

- [ ] 未审批时无法 commit 或 push。
- [ ] 审批后严格按照 commit → 拉取最新代码 → push 执行。
- [ ] 拉取冲突时不执行 push，并明确提示人工合并。
- [ ] push 失败时不更新工单。
- [ ] 防止重复点击造成重复 commit、push 或工单更新。

### AC-05 工单流转与恢复

- [ ] “待测试”工单不显示“去解决”，详情不显示 AI 相关功能。
- [ ] 需求工单经人工审批和 push 成功后只改为“待测试”，负责人不变。
- [ ] Bug/支持工单经人工审批和 push 成功后改为“待测试”并转交创建人；缺少创建人时禁止审批。
- [ ] 其他工单类型按审批时人工指定的负责人流转。
- [ ] 工单更新失败时标记为部分完成，只重试该步骤。
- [ ] 应用重启后能够识别未完成或部分完成任务。
- [ ] 恢复任务时不会自动执行 commit、push 或工单更新。
- [ ] 执行历史能够追溯工单、仓库、AI、commit 和最终结果。

### AC-06 实际运行验证

- [ ] 应用在目标 Mac 上能够安装或直接启动。
- [ ] 使用真实知识库会话完成工单同步验证。
- [ ] 使用测试工单和测试仓库分别完成 Codex、Cursor 流程验证。
- [ ] 实际验证正常 push 流程、拉取冲突阻断和工单更新失败恢复。
- [ ] 按本文档逐项记录通过、失败和修复结果；失败项修复后重新验证。

## 15. 实现约束

- 开发前确认本文档；当前冻结基线为 v1.1，后续变更继续通过 CR 编号增量记录。
- 组件使用语义主题变量，禁止为暗黑模式复制两套页面。
- 知识库自动化、AI 编排、Git 操作和 UI 展示分层实现，避免页面逻辑直接执行高风险命令。
- Git 与工单更新步骤必须设计成可恢复、可幂等执行。
- 所有高风险操作必须以当前真实状态为准，不能仅依赖缓存判断。
- 不因实现方便而删除视觉图中的项目导航、卡片详情或“去解决”入口；详情展示必须遵循 CR-001 的居中弹窗规则。
- 不因视觉图未展示而省略加载、异常、恢复和审批安全机制。

## 16. 需求变更规则

### 16.1 变更流程

每次新增或修改需求时，先新增一条变更记录：

```text
变更编号：CR-XXX
提出日期：YYYY-MM-DD
变更内容：
变更原因：
影响的需求编号：
影响的页面或流程：
是否影响数据或已有配置：
新增或修改的验收项：
状态：待确认 / 已确认 / 已完成 / 已拒绝
```

### 16.2 执行规则

- 已确认需求不得静默删除或改写。
- 视觉调整默认只影响指定组件，不扩散到其他页面。
- 功能变更必须同步更新状态机、异常场景和验收项。
- 若新需求与旧需求冲突，必须明确指出冲突并由用户选择，不自行覆盖。
- 代码实现与文档不一致时，先修正文档或实现差异，再继续扩展。
- 每次交付都要列出本次实际变更对应的需求编号。

## 18. 待确认结论

当前基线确认：

- v1.0 按提供的设计图开发，不将知识库网页作为主界面。
- 工单详情采用居中实色弹窗和半透明遮罩，不采用右侧详情页、侧栏或毛玻璃效果。
- 应用优先展示最近成功同步的缓存工单，并在启动后与设定间隔内后台同步。
- 工单进入“待测试”后的操作限制和交付转派遵循 FR-210 与 FR-700。
- 知识库网页仅用于登录、后台数据获取、工单更新及查看原工单。
- 浅色和暗黑模式均属于 v1.0 必须验收的功能。
- Git 与工单外部操作必须遵循人工审批和失败阻断规则。
- 后续需求通过变更单增量管理，不直接覆盖本基线。
